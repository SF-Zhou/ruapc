# QP registry experiment

This experiment compares the CQ-dependent WRID implementation at baseline
commit `36682aec6332b526b08724030999f7e2f24c5071` with the new QP registry.
The new design uses two type bits and 62 sequence bits. Completion identity
includes the originating CQ, hardware QPN, WRType/direction and sequence; counters are
per QP, not globally unique across a CQ. A retirement watermark prevents an
old identity from matching a reused hardware QPN.

## Completed evidence

The measured current implementation has the 184-file Rust/Cargo digest
`cf91cd3502051d436d5028abce86aa3ec550b3255048fddf864f72031ce6b985`.
All six benchmark sources and the lock are byte-identical between the two
measured versions. The production changes are the variable being compared.

- [capacity-summary.json](capacity-summary.json) indexes all six capacity
  observations with compressed and uncompressed SHA256 values. A CQ with
  actual capacity 15 held 20000 live QPs in the current implementation and
  verified a 64-byte SEND/RECV between the final two. The baseline reached
  `CompletionRoutesExhausted` at 15 live QPs. Both application versions
  established 20000 healthy stripes per endpoint with R8, then verified every
  one of the 40000 serial round-robin echoes and shut down normally.
- [echo-long-paired.json](echo-long-paired.json) retains all ten echo runs.
- [rpc-paired.json](rpc-paired.json) indexes all twenty 128/256-stripe runs,
  including the SHA256 of each gzip artifact and its original JSON content.
- [remote-memory-extended-paired.json](remote-memory-extended-paired.json)
  retains all ten stock remote-memory runs.
- [paired-summary.json](paired-summary.json), generated by
  [summarize.py](summarize.py), provides both version medians, every paired
  value/change and the five-pair range for all 22 measured metrics. Run
  `python3 docs/qp-registry-data/summarize.py` to regenerate it.
- [integrity.json](integrity.json) records the final source, native input,
  dependency, immutable executable and raw-artifact verification, including
  exact path counts, completion checks and CPU placement.
- [checks.json](checks.json), [tests.log](tests.log) and
  [clippy.log](clippy.log) contain the parent task's production validation.

There are 46 new measured process runs: six capacity observations and forty
performance runs forming twenty alternating pairs. Every process returned
zero, with no timeout or truncated JSON. The two baseline small-CQ probes
explicitly report capacity failure; they are expected limit observations,
not successful exchanges. No completed sample or outlier was removed.

The four echo QPS paired medians range from -1.09% to +0.89%. At 1024 tasks,
128/256 stripes show -1.52%/-3.91% paired QPS changes, with all five pairs
negative in each case. These are measured costs. Remote memory has wider
variation: 1 MiB READ paired throughput is -3.79% (range -14.68% to +7.15%),
and the first pair is substantially slower in both versions. This experiment
does not establish zero regression across workloads. The complete comparison
and interpretation are in [the implementation report](../qp-registry.md).

## Baseline provenance

The baseline's 184-file Rust/Cargo source digest is
`af6fab2d623ebe602a5df9b17f5595964c323cf604bd9d4b2c303f6dd63af45f`.
It and the dependency lock exactly match the final implementation measured
in [the preceding experiment](../rdma-capacity-data/final/README.md).
Every reused immutable executable was checked against its recorded SHA256
and copied to a new experiment directory. The baseline source is separately
archived from the clean commit. `source-metadata.json` records the full
Rust/Cargo source set, lock, binary fingerprints and prior build provenance.
The compiled C shim and bindgen header are separately fingerprinted and identical
in baseline, current, and the reused build snapshot.

The earlier experiment's raw samples are historical evidence. New paired
measurements run the immutable baseline executables again alongside the new
implementation so that they share the same current host conditions.

Two new low-level capacity harnesses use interfaces available in both versions
and were compiled with an independent fresh baseline Cargo target. The common
harness sources are byte-identical between versions. All other benchmark
sources are reused unchanged from the preceding experiment.

## Workloads

- `registry_qps.rs`: requests a CQ with eight entries and creates 20000 RC QPs
  with SQ/RQ capacities of four. No work requests are posted. It retains all
  QPs simultaneously, checks common send/receive CQ ownership and unique
  hardware QPNs, records actual provider CQ/depth values, and destroys every QP.
  CQ entry capacity therefore does not justify limiting this idle registry.
- `registry_exchange.rs`: the same small CQ and 20000 simultaneous QPs, then
  connects only the last two. It posts one 64-byte receive and one SEND,
  dispatches the CQ-issued completion tokens by QPN, calls `QueuePair::complete`,
  and verifies the full payload. Only two CQEs are produced. The baseline and
  new implementation use the identical source without route-slot APIs.
- [capacity_rpc_large_trace.rs](../rdma-capacity-data/capacity_rpc_large_trace.rs): application capacity on one CQ per endpoint,
  20000 stripes, default SQ/RQ capacities 64, R8 receive rings, 16 KiB message
  buffers, 4 GiB pool limit per endpoint and CQ request 524288. It checks exact
  healthy path counts and all 40000 serial round-robin echoes before shutdown.
  The timeout is 300 s, connect deadline 120 s and lease 300 s. This is capacity
  and full-sweep validation, separate from concurrent throughput measurements.
- Extended `echo`: five alternating baseline/current pairs with 2.56 million
  concurrent requests per case, 64/1024 tasks, one/two server endpoints,
  5000 warmup and 50000 measured serial requests. The existing
  [echo-long.patch](../rdma-capacity-data/echo-long.patch) is the same
  benchmark-only request-count change in both versions.
- [capacity_rpc.rs](../rdma-capacity-data/capacity_rpc.rs): five alternating pairs for each of 128 and 256 stripes,
  with 2.56 million requests at each of 64/1024 tasks. Both versions use the
  same default SQ/RQ capacities, R8, 16 KiB messages and 512 MiB pool limit per
  endpoint. Setup and report serialization are outside throughput timing.
- Stock `remote_memory`: five alternating pairs with 1000 warmup and 10000
  measured operations per direction/size, including 1 MiB. Complete payload
  verification remains inside the measured workload. Additional diagnosis is
  undertaken only if the completed results require it; all samples remain.

Hardware limits and the refreshed read-only query are recorded in
`hardware.json` and `mlx5_0-devinfo.txt`. The device is fixed to mlx5_0 with
NUMA node 0 memory. The pinning shim places main on CPU 8, runtime workers on
CPUs 0–7 (0–3 for remote memory) and the two endpoint pollers on CPUs 9–10.
No benchmark processes overlap and builds/tests remain stopped during samples.
The 20000-stripe R8 probe previously used about 8–9 GiB resident memory on this
host, within the 128 GiB container limit; the low-level probes use far less.

## Building and running

Use independent source archives and Cargo targets for baseline and current.
Copy [the archived Cargo.lock](Cargo.lock) to each source tree. Copy the two local
`registry_*` Rust files and the two linked application capacity sources into
`ruapc/benches`, adding corresponding `[[bench]]` entries with `harness = false`.
The unchanged application harnesses, echo patch, paired runner and pinning
source are referenced from the preceding committed experiment rather than
duplicated; their exact hashes are in `existing_harness_dependencies_sha256`.
Apply the linked `echo-long.patch` to both echo sources.

Compile with a fresh per-version target:

```sh
CARGO_TARGET_DIR=/tmp/qp-registry-current-fresh-target cargo bench -p ruapc --locked --no-run --bench echo --bench remote_memory --bench capacity_rpc --bench capacity_rpc_large_trace --bench registry_qps --bench registry_exchange
```

Copy emitted executables to immutable names before running samples. `source-metadata.json` records actual build commands and fingerprints.
Do not point an archive at the mutable workspace target: older archive mtimes
can otherwise cause Cargo to reuse artifacts from a different source tree.

Use `run_capacity.py` for one probe, the existing
[run_paired.py](../rdma-capacity-data/run_paired.py) for echo/remote memory,
and `run_multiconn.py` for 128/256 stripes. Pass `--pin-library` explicitly.
The capacity runner records the requested timeout and preserves raw output
if a timeout truncates the last JSON line. Parsable events and JSON parse
errors are recorded separately. Expected baseline capacity failures are data,
not successful exchanges; check the phase/error fields as well as returncode.

Full application path reports are retained as deterministic gzip JSON to avoid
repeating thousands of verbose path rows in the textual diff. The multi-stripe
index records both compressed and original content SHA256 for each raw file.
Small summaries and paired benchmark output remain normal JSON. Read either
format with `read_artifact.py`; `--summary` prints counts and CQ reports while
leaving the full data intact:

```sh
python3 docs/qp-registry-data/read_artifact.py docs/qp-registry-data/rpc-128-current-1.json.gz --summary
```

For a new run, first compile the pinning library from its recorded source:

```sh
cc -O2 -shared -fPIC -o /tmp/qp-registry-pin.so docs/rdma-capacity-data/pin_threads.c -ldl -pthread
```

The actual workload commands below use the recorded immutable binary paths;
substitute newly built binaries and a new output directory to reproduce them.
Run these commands serially after all builds and tests have stopped:

```sh
mkdir -p /tmp/qp-registry-results
for version in baseline current; do
  python3 docs/qp-registry-data/run_capacity.py --binary /tmp/ruapc-qp-registry-bench/registry-qps-$version --pin-library /tmp/qp-registry-pin.so --output /tmp/qp-registry-results/$version-small-cq-qps.json --env RUAPC_CAPACITY_QPS=20000 --env RUAPC_CAPACITY_CQ_LEN=8
  python3 docs/qp-registry-data/run_capacity.py --binary /tmp/ruapc-qp-registry-bench/registry-exchange-$version --pin-library /tmp/qp-registry-pin.so --output /tmp/qp-registry-results/$version-small-cq-exchange.json --env RUAPC_CAPACITY_QPS=20000 --env RUAPC_CAPACITY_CQ_LEN=8
  python3 docs/qp-registry-data/run_capacity.py --binary /tmp/ruapc-qp-registry-bench/capacity-rpc-large-trace-$version --pin-library /tmp/qp-registry-pin.so --output /tmp/qp-registry-results/$version-rpc-20000-r8.json.gz --timeout 300 --env RUAPC_CAPACITY_CONNECTIONS=20000 --env RUAPC_CAPACITY_TOTAL_OPS=0 --env RUAPC_CAPACITY_CQ_LEN=524288 --env RUAPC_CAPACITY_RECV=8 --env RUAPC_CAPACITY_POOL_GIB=4
done
python3 docs/rdma-capacity-data/run_paired.py --baseline /tmp/ruapc-qp-registry-bench/echo-baseline-long --current /tmp/ruapc-qp-registry-bench/echo-current-long --pin-library /tmp/qp-registry-pin.so --output /tmp/qp-registry-results/echo-long-paired.json --pairs 5
python3 docs/qp-registry-data/run_multiconn.py --baseline /tmp/ruapc-qp-registry-bench/capacity-rpc-baseline --current /tmp/ruapc-qp-registry-bench/capacity-rpc-current --pin-library /tmp/qp-registry-pin.so --output-dir /tmp/qp-registry-results --pairs 5 --connections 128 256
python3 docs/rdma-capacity-data/run_paired.py --baseline /tmp/ruapc-qp-registry-bench/remote-memory-baseline --current /tmp/ruapc-qp-registry-bench/remote-memory-current --pin-library /tmp/qp-registry-pin.so --output /tmp/qp-registry-results/remote-memory-extended-paired.json --pairs 5 --kind remote_memory --warmup 1000 --serial 10000
```

Exact measurement order, environment, wall time and executable/pinning hashes
are retained in each raw artifact. Capacity observations are single runs per
version; only the throughput/latency groups use five alternating pairs.
